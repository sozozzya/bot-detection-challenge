# Bot Detection

## 1. Задача

Необходимо определить, насколько `cookie_id` относится к трафику известных сервисов автоматизированного сбора данных.

- `target = 1` - трафик известных сервисов автоматизированного сбора данных;
- `target = 0` - трафик, отнесенный к человеческому;
- для каждой `cookie_id` необходимо получить непрерывный `score` в диапазоне `[0, 1]`;
- чем выше `score`, тем выше приоритет cookie как потенциально автоматизированного трафика.

Основная метрика задачи - **Precision при Recall >= 0.70 (`P@R>=0.70`)**. Порог классификации в submission не передается: проверяющая система самостоятельно рассматривает пороги и выбирает максимальный precision среди тех, где recall не ниже 70%.

Признаки должны быть доступны к моменту окончания индивидуального суточного окна наблюдения соответствующей cookie.

---

## 2. Основная идея решения

Финальное решение рассматривает каждую `cookie_id` как отдельный объект классификации и агрегирует ее историю событий внутри соответствующего 24-часового окна.

Общий pipeline:

```text
train.csv / test.csv
        +
events.csv.gz
        ↓
индивидуальная фильтрация событий по [window_start_ts, window_end_ts)
        ↓
cookie-level feature engineering
        ↓
единая числовая feature matrix
        ↓
CatBoostClassifier
        ↓
predict_proba(... )[:, 1]
        ↓
проверка submission
        ↓
submission.csv
```

Ключевая гипотеза решения: автоматизированный трафик может отличаться от человеческого не только общим количеством событий, но и:

1. разнообразием активности;
2. структурой типов событий;
3. временным паттерном поведения;
4. интенсивностью и регулярностью последовательности событий.

Поэтому признаки строятся на уровне всей истории cookie внутри разрешенного окна, а не на уровне отдельных событий.

# 5. `01_data_audit.ipynb` - аудит данных

## Цель

Перед построением признаков проверить, что исходные данные корректны, а используемая схема observation window соответствует условию задачи.

В ноутбуке **не выполняется обучение модели и не производится подбор гиперпараметров**.

Проверяются:

- структура и типы данных;
- обязательные столбцы;
- уникальность `cookie_id`;
- пересечение train/test;
- целевая переменная;
- временные границы;
- длительность observation window;
- возраст cookie;
- структура `events.csv.gz`;
- покрытие событий;
- распределение `event_name`;
- соответствие `eid` и `event_name`;
- значения `platform`;
- User-Agent;
- пропуски;
- дубликаты;
- порядок событий;
- временное распределение train/test;
- распределение target по времени;
- события внутри и вне observation window.

## Ключевая проверка временного окна

Для каждой cookie используется только:

```text
window_start_ts <= event_ts < window_end_ts
```

То есть событие, произошедшее раньше начала окна или начиная с `window_end_ts`, не используется при построении признаков.

Эта проверка выполняется отдельно на этапе аудита и затем реализуется в финальном pipeline.

## Проверка временной структуры данных

Аудит показывает, что train и test разделены по времени, поэтому случайное перемешивание объектов при валидации не является оптимальным способом оценки.

Это стало основанием для использования time-based и walk-forward validation на следующих этапах.

## Пропуски

Исследуется доля пропусков в event-level полях.

Пропуски интерпретируются с учетом типа события: например, `search_query`, `item_id`, `seller_type`, координаты курсора и другие поля заполнены не для всех событий.

На финальном этапе сырые пропуски не передаются в модель: используются агрегированные cookie-level признаки, а отсутствующие event-derived агрегаты для cookie без соответствующих событий заполняются нулевыми значениями.

## Дубликаты

На этапе аудита отдельно проверяются повторяющиеся строки событий и различные варианты дублирования.

В финальном pipeline **нет безусловного `drop_duplicates()`**. Это сделано намеренно: одинаковые значения отдельных полей не являются достаточным основанием считать события ошибочными дублями, а удаление строк может изменить показатели интенсивности поведения.

Финальный pipeline использует ту же логику обработки событий, на которой получены validation results.

# 6. `02_feature_engineering.ipynb` - построение и исследование признаков

## Цель

Построить поведенческие признаки на уровне `cookie_id` и проверить, какие группы признаков действительно улучшают качество детекции.

Основная метрика:

```text
P@R>=0.70
```

Дополнительные диагностические метрики:

- PR-AUC;
- ROC-AUC.

## Правила экспериментов

Во всех экспериментах:

1. используются только события внутри `[window_start_ts, window_end_ts)`;
2. `cookie_id` не используется как признак;
3. test не используется для выбора признаков;
4. validation split выполняется по времени;
5. сравнение групп признаков выполняется на одном и том же validation split;
6. основная метрика соответствует официальной реализации из `metric.py`.

Следующая гипотеза: двух cookie может быть одинаковое количество событий и одинаковое число типов действий, но совершенно разная структура поведения.

Поэтому для каждого наблюдаемого типа события рассчитываются:

- абсолютное количество событий;

- `search_results_view`;

- `favorite_add`;
- `seller_page_view`;
- `contact_phone_show`;
- `login`;
- `contact_chat_open`;
- `contact_message_sent`.

Результат:

```text

```

Добавление структуры событий улучшает качество относительно E01.

## Experiment 03. Temporal behavior

Временное поведение является следующей ключевой группой признаков.

Для каждой cookie рассчитываются:

- `first_event_offset_seconds`;
- `last_event_offset_seconds`;
- `n_active_hours`;
- `mean_inter_event_seconds`;
- `median_inter_event_seconds`;
- `std_inter_event_seconds`;
- `min_inter_event_seconds`;
- `max_inter_event_seconds`;
- `active_span_seconds`;
- `events_per_active_hour`;
- `inter_event_burstiness`.

### Что описывают признаки

`first_event_offset_seconds` и `last_event_offset_seconds` описывают положение активности внутри окна.

`active_span_seconds` характеризует продолжительность активного периода.

`n_active_hours` показывает, в скольких часах окна происходили события.

`mean/median/std/min/max_inter_event_seconds` описывают интервалы между последовательными событиями.

`events_per_active_hour` характеризует интенсивность активности относительно продолжительности наблюдаемого активного периода.

`inter_event_burstiness` используется как нормированная характеристика вариативности межсобытийных интервалов.

Результат:

```text
P@R>=0.70 = 0.332264
PR-AUC     = 0.606980
ROC-AUC    = 0.850155
```

Именно E03 стал основным feature set для следующего этапа сравнения моделей.

Дополнительно исследовались технические характеристики клиентского трафика.

Для User-Agent проверялись:

- семейство ОС;
- семейство браузера;
- mobile/desktop;
- признаки headless/automation;

- количество уникальных User-Agent внутри cookie.

Для `platform` дополнительно нормализовался регистр значений.

При этом raw User-Agent не подавался в модель напрямую из-за высокой кардинальности.

Результат объединения E03 с техническими признаками:

```text

```

Основная метрика ухудшилась относительно E03:

```text

E03 + E04 → 0.302217
```

Поэтому User-Agent и дополнительные platform features **не вошли в финальный feature set**.

Нормализованный `platform` используется только в финальном агрегате `n_unique_platforms`.

# 8. `03_model_experiments.ipynb` - сравнение моделей

## Цель

На фиксированном E03 feature set сравнить разные классы моделей и выбрать вариант для финального решения.

Перед обучением выполняется канонизация признаков:

- проверяются `NaN` и конечность значений.

Точные дубликаты признаков определяются по train и затем те же колонки удаляются из test.

# 9. Валидация

## Основной validation split

Для непосредственного сравнения с предыдущими экспериментами используется временной split:

```text
train:
    window_start_ts < 2026-04-17

validation:
    window_start_ts >= 2026-04-17
```

Такой split сохраняет временной порядок и не позволяет обучению использовать будущие относительно validation наблюдения.

## Дополнительная проверка устойчивости

Для окончательного выбора модели используется walk-forward validation.

Для каждой validation date:

```text
train = только более ранние даты
validation = только текущая дата
```

Проверяются даты:

```text
2026-04-17
2026-04-18
2026-04-19
```

Таким образом, оценка приближена к реальному сценарию, в котором модель обучается на прошлом трафике и применяется к следующему временному периоду.

Основной критерий выбора:

```text
pooled P@R>=0.70
```

Дополнительно анализируются:

- средний daily P@R;
- PR-AUC;
- ROC-AUC.

# 10. Сравнение моделей

## Основной validation split

На исходном временном split были получены:

| Model | P@R>=0.70 |
|---|---:|
| Random Forest, `leaf=10` | 0.442688 |
| HistGradientBoosting | 0.441406 |
| CatBoost | 0.434109 |
| Random Forest, `leaf=3` | 0.430769 |
| Random Forest, `leaf=5` | 0.424812 |
| Random Forest, `leaf=1` | 0.422642 |
| Logistic Regression | 0.270531 |

Эти результаты использовались как первичное сравнение.

## Walk-forward validation

Для окончательного выбора сравнивались три наиболее перспективных кандидата:

| Model | P@R>=0.70 pooled | Mean daily P@R | PR-AUC pooled | ROC-AUC pooled |
|---|---:|---:|---:|---:|
| **CatBoost** | **0.4575** | **0.5208** | 0.6695 | 0.8856 |
| HistGradientBoosting | 0.4427 | 0.4903 | **0.6807** | 0.8861 |
| Random Forest, `min_samples_leaf=10` | 0.4308 | 0.4103 | 0.5955 | 0.8721 |

Основной критерий - pooled `P@R>=0.70`, поскольку именно эта метрика указана в задании.

Поэтому для финального pipeline выбран **CatBoost**.

Важно: значение `0.4575` - это только внутренний результат walk-forward validation на размеченном train. Оно не является результатом скрытого теста.

# 13. Почему в submission не применяется threshold

Задача требует передать непрерывный `score`, а не бинарный ответ.

Поэтому используется:

```python
model.predict_proba(X_test[feature_cols])[:, 1]
```

и в submission записывается полный ranking score.

Фиксированный порог вроде `0.5` не используется.

Это важно, потому что официальная метрика сама рассматривает возможные thresholds и выбирает максимальный precision среди порогов с recall не ниже 70%.

# 14. Обработка пропусков

Event-level данные содержат пропуски в полях, которые применимы только к определенным типам событий.

В финальной модели исходные категориальные поля не передаются как сырые категориальные значения.

Вместо этого используются агрегаты:

- `n_unique_items`;
- `n_unique_categories`;
- `n_unique_locations`;
- `n_unique_search_queries`;
- `n_unique_event_types`;
- `n_unique_platforms`;

а также количества и доли типов событий.

Cookie без событий не теряются: metadata сохраняется, а отсутствующие event-derived агрегаты после `left join` заполняются нулями.

Перед обучением дополнительно проверяется:

- отсутствие `NaN`;
- отсутствие `inf`;
- отсутствие `-inf`;
- одинаковая схема train/test;
- отсутствие `cookie_id` среди model features.

---

# 15. Обработка категориальных признаков

Категориальные поля:

- `event_name`;
- `platform`;
- `item_category`;
- `item_location`;
- `seller_type`;
- `search_query`;
- `search_page`

не передаются в финальную модель в исходном виде.

Вместо этого они используются для формирования устойчивых cookie-level агрегатов и event distribution features.

Такой подход:

- снижает зависимость от высокой кардинальности отдельных значений;
- обеспечивает единую числовую схему train/test;
- позволяет описывать поведение cookie через структуру ее активности.

Отдельно исследовался User-Agent. Raw User-Agent в финальную модель не включен, а эксперимент E04 показал ухудшение основной метрики относительно E03.

---

# 16. Обработка дубликатов

На этапе аудита были исследованы повторяющиеся event-level строки.

В финальном pipeline не используется безусловный:

```python
drop_duplicates()
```

Причина: одинаковые значения доступных полей не доказывают, что строки являются ошибочно продублированными событиями. Автоматическое удаление могло бы изменить:

- `n_events`;
- event counts;
- event shares;
- inter-event statistics;
- другие поведенческие признаки.

Поэтому используется исходная история событий и единое правило временного фильтра.

---

# 17. Контроль утечки данных

Контроль leakage является обязательной частью pipeline.

Сначала события ограничиваются индивидуальным observation window:

```text
window_start_ts <= event_ts < window_end_ts
```

и только после этого строятся агрегаты.

В модель не передаются:

- `target` как признак;
- `cookie_id` как признак;
- события после `window_end_ts`;
- test labels;
- внешние данные;
- ручные решения для отдельных cookie.

Test не используется для выбора признаков или моделей.

Во время разработки не выполнялось ручное восстановление скрытой тестовой разметки и не задавались hardcoded scores для отдельных `cookie_id`.

# 18. Ограничения задания

Финальное решение соответствует заданным ограничениям:

- LLM с количеством параметров более 1B не используется;
- внешние API не используются;
- тестовые данные вручную не размечаются;
- hardcoded scores для конкретных `cookie_id` отсутствуют;
- скрытые test labels не восстанавливаются;
- решения других кандидатов не используются;
- применяются локальные open-source библиотеки;
- random seed фиксирован;
- версии зависимостей зафиксированы.

Используемые open-source библиотеки:

- **CatBoost** - финальная модель градиентного бустинга;
- **pandas** - загрузка и обработка данных, feature engineering;
- **NumPy** - численные операции и проверки;
- **scikit-learn** - baseline и исследовательское сравнение моделей.

# 20. Проверка submission

Финальный код проверяет:

- наличие ровно двух колонок;
- колонки `cookie_id` и `score`;
- количество строк, совпадающее с `test.csv`;
- уникальность `cookie_id`;
- полное совпадение множества test `cookie_id`;
- отсутствие пропусков;
- отсутствие бесконечных значений;
- нахождение всех `score` в `[0, 1]`.

Итоговый формат:

```text
cookie_id,score
```

Для каждой `cookie_id` из `test.csv` должна присутствовать ровно одна строка.

# 21. Итог исследования

Исследование показало последовательное улучшение качества:

| Этап | P@R>=0.70 | PR-AUC | ROC-AUC |
|---|---:|---:|---:|
| E00 - baseline | 0.102470 | 0.174609 | 0.607396 |
| E01 - activity | 0.210037 | 0.379974 | 0.790239 |
| E02 - event distribution | 0.242424 | 0.473567 | 0.810268 |
| E03 - temporal behaviour | **0.332264** | **0.606980** | **0.850155** |
| E04 - User-Agent + platform | 0.302217 | 0.603115 | 0.850368 |

Основной вывод feature engineering:

> Для данной задачи существенный сигнал содержится не только в количестве действий cookie, но и в структуре и временной организации ее поведения.

После фиксации E03 feature set было проведено сравнение моделей. Walk-forward validation показала:

```text
CatBoost                    0.4575
HistGradientBoosting        0.4427
Random Forest                0.4308
```

По основной метрике `P@R>=0.70` выбран CatBoost.

Финальная модель обучается на полном размеченном train и формирует непрерывные `score` для всех test cookies.
